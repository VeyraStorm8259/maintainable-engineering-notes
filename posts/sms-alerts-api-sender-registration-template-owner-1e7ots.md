# SMS Alerts API Sender Registration — Template Ownership and Delivery Tracking Retention

The bill for sending a generated media report includes rendering, retained attachments, email transport, SMS attempts, and the operational work of maintaining sender registrations and delivery evidence. Short answer: choose an SMS alerts API by its registration boundaries and evidence model, while keeping report templates under explicit ownership; then budget attachment retention separately from dispatch history. An easy send call answers very little about what a later resend will contain.

Consider a planning example, not a measured workload: 100 reports per day, each with a 6 MiB attachment, kept for 30 days. That is 18,000 MiB of attachment payload at steady state before replicas or transport copies. Reducing attachment retention to 7 days makes the same term 4,200 MiB. This identifies the dominant retained-payload term in the example, not the largest charge on an unknown provider's invoice. Financial dominance depends on contracted storage, delivery, and processing rates.

For a media operations team dispatching field crews, email carries the generated assignment report; SMS says that the assignment is ready. The central question is who owns the subject, body, attachment selection, and revision history when an editor corrects an assignment after dispatch. Sender registration and delivery tracking matter, but neither can reconstruct an attachment that has been overwritten.

## What are you paying to preserve?

Count retained objects before debating integration convenience. A template definition is one object; a particular rendering is another; the email representation and delivery receipt are different evidence again. Keeping all four indefinitely makes the retention policy easy to describe and expensive to justify. Keeping only the template makes a historical resend ambiguous whenever the template, source data, or renderer has changed.

Bytes aren't evidence.

The 30-day example retains 3,000 attachments. Saving a second full attachment copy per report doubles the attachment-payload term, whereas referencing the same immutable artifact from separate attempt records does not create that second application-level copy. This is accounting arithmetic, not a promise about a storage system's physical replication. Ask which copies the application creates and which copies the storage contract bills.

There is also transport expansion to budget. RFC 2045 encodes three input octets into four Base64 characters, before line breaks and MIME headers; a 6 MiB attachment therefore becomes 8 MiB of Base64 characters before those additions. That expansion concerns the email representation. It does not justify multiplying every stored report by the same factor unless the application retains that representation.

The change that moves this storage term is short attachment retention with longer-lived metadata, provided the business accepts the resulting replay boundary. Determine whether the team needs to send the exact historical document, generate a fresh report from historical inputs, or merely explain the original dispatch.

Those are three different requirements.

## Template ownership fixes the replay boundary

Treat the assignment report and its notification as one release decision even when different systems render them. Record a template revision, artifact identifier, and dispatch identifier together. A revision label alone is insufficient if someone can edit the content behind that label.

| Ownership choice | What the team must preserve | Trade-off during a correction |
| --- | --- | --- |
| Application owns report and notification templates | Released content, renderer version, artifact reference | One review covers both channels, but the application team maintains rendering and release tests |
| Delivery service owns the notification template | External template revision plus the application's report revision | Editors get a separate release path, but reproduction depends on both revision histories |
| Ownership is split by channel | A mapping of email, SMS, and report revisions | Channels evolve independently, but mismatched revisions become a dispatch failure mode |

No option earns a recommendation merely by reducing integration code. The acceptance test is a corrected crew assignment: after revision B exists, can the system explain which recipients received revision A and which artifact their email attached? If a resend silently renders B under A's dispatch identifier, the history is misleading even if both sends succeeded.

Name that failure mode: revision drift. Another is attachment substitution, where a stable object key points to newly generated bytes. An immutable artifact reference prevents that substitution only if the storage layer enforces the immutability the application assumes; a digest records byte identity but does not provide durability, access control, or retention enforcement.

## Keep attachment construction separate from dispatch attempts

This Python example makes the ownership boundary visible. Its local 6 MiB limit is an application policy chosen for the example, not an email-provider limit. The function constructs a message and an evidence record; the caller persists the artifact and record before scheduling delivery.

```python
from email.message import EmailMessage
from email.policy import SMTP
from hashlib import sha256

MAX_REPORT_BYTES = 6 * 1024 * 1024

def prepare_report(pdf: bytes, recipient: str, artifact_id: str):
    if not pdf or len(pdf) > MAX_REPORT_BYTES:
        raise ValueError("Report must contain between 1 byte and 6 MiB")

    template_revision = "crew-assignment-v3"
    message = EmailMessage(policy=SMTP)
    message["From"] = "dispatch@media.example"
    message["To"] = recipient
    message["Subject"] = "Field crew assignment report"
    message.set_content("Your generated assignment report is attached.")
    message.add_attachment(
        pdf, maintype="application", subtype="pdf",
        filename="crew-assignment.pdf",
    )
    evidence = {
        "artifact_id": artifact_id,
        "attachment_sha256": sha256(pdf).hexdigest(),
        "attachment_bytes": len(pdf),
        "template_owner": "application",
        "template_revision": template_revision,
    }
    return message, evidence
```

The function labels the supplied bytes as a PDF; it does not validate their contents. Validate the generated document upstream, and check serialized message size against the selected transport's documented limit before queueing it. Python's email library supports MIME attachment construction, but constructing a message does not authenticate a sender or send anything.

Persist the report and dispatch intent before a worker attempts either channel. Give each transport attempt its own identifier and retain its relationship to the logical dispatch, so a retry is distinguishable from a new assignment. An uncertain result needs reconciliation: blindly replaying a send can produce duplicate notifications, while assuming success can leave a crew uninformed. The selected API's documented retry and deduplication behavior determines how the worker resolves that uncertainty.

Test the byte boundary with a generated fixture, verify that a correction gets a distinct artifact reference, and exercise a crash between dispatch persistence and transport acknowledgment. The last case is where an integration demo often stops being useful.

## How should an SMS alerts API separate sender registration from delivery tracking?

For US application-to-person traffic over local ten-digit numbers, the cited A2P 10DLC documentation describes brand and campaign registration. Scope matters: that documentation covers a particular sender route, not every US sender type or every European destination. Make the intended sender type and destination explicit before estimating integration work.

Do not collapse Europe into a single sender-ID checkbox. For each launch country, require current evidence for the proposed sender type, registration requirements, recipient permission, and withdrawal process, and have the responsible compliance reviewer approve the actual notification purpose. An assignment alert to a crew member and a promotional message to a subscriber should not inherit the same assumptions just because one endpoint can submit both.

For email, the cited sender guidelines describe authentication requirements, with additional requirements for bulk senders. Template ownership does not transfer responsibility for configuring the sending domain. Verify the applicable requirements before release and after a change to the delivery path.

The tracking model should distinguish application submission, transport acceptance, reported delivery, and human acknowledgment. Reported delivery is not proof that a crew member read an assignment or opened its attachment. If dispatch requires acknowledgment, model an explicit action and deadline rather than relabeling a transport callback as completion.

Tie callback processing to attempt identifiers, and exercise duplicate and out-of-order events in the integration test environment. Require documented callback authentication and event semantics from any candidate service. The useful selection question is whether the evidence can be reconciled after a timeout, not whether a dashboard displays a reassuring aggregate percentage.

## Decide what expires before the first dispatch

A deployment gate can be small: confirm template ownership, exercise the correction-and-resend test, verify sender readiness for each route, and establish who investigates unresolved delivery attempts. Observe retained attachment bytes, artifact lookup failures, duplicate attempts, revision mismatches, and acknowledgment delays. Copying full reports into logs creates another retention surface with no automatic replay benefit.

The proposed policy deliberately stops keeping attachment bytes after the chosen replay window. It also avoids retaining a complete encoded email merely to duplicate an attachment already stored elsewhere. Keep the dispatch-to-artifact mapping, digest, template revision, and attempt history only for a separately justified audit period, with access controls appropriate to assignment data. No universal retention duration follows from the messaging standards cited here.

That deletion has a cost. After the artifact expires, a digest can help compare a separately recovered copy, but it cannot reconstruct the original report. If a crew disputes an old assignment, retained metadata may explain the dispatch while leaving the exact attachment unavailable. Extending the replay window buys that forensic capability with retained bytes and access-control obligations; shortening it deliberately gives the capability up.

Approve that loss explicitly.
